# 电商售后 Agent Demo：第一轮大模型评测报告

- 时间：2026-10-10 晚（北京时间）
- 被测对象：Dify 云端 Agent「电商售后 Agent Demo」，模型 deepseek-v4-flash，Function Calling，5 个自定义工具，后端为 ngrok 上的 mock 服务
- 方法：通过 `POST /chat-messages`（streaming 模式）逐条跑 30 条用例，每条用例新开一个会话，user 设为 eval-runner；多轮用例按 ｜ 分隔的脚本依次发送。**每条用例开始前都重启 mock 后端**，清空内存里的工单（包括此前 UI 测试留下的工单），保证用例之间互不影响。TC30 是商家端用例：先重放 TC06 的对话脚本，再查询商家 M01 收到的工单
- 原始记录：`eval/transcripts.jsonl`；每条用例的后端日志：`eval/uvicorn_logs/TCxx.log`；逐条判定：`测试用例_评测结果.xlsx` 的「LLM评测记录」页
- 这是单次运行的结果，样本量小，模型输出也有随机性，只能作为方向参考

## 3. 失败与 PARTIAL 的原因

**原因 A：用例脚本和提示词里的“先确认再建单”冲突（8 条：TC01–08，连带 TC30）**
提示词第 5 步要求先向用户复述方案、得到确认再建单，而单轮用例的脚本里没有“确认”这一轮。模型的方案基本都对，但每次都停在“请确认”这一步，所以解决率被拉低。这主要是**评测设计的问题，不完全是模型的问题**。TC30 依赖 TC06 走完建单，同样卡在了这里。

**原因 B：风险信号压过了用户的真实诉求（TC28，以及 TC27 的一部分）**
PD1008 的买家近 30 天售后 4 次，模型因此在一个纯物流查询里也转了人工、建了工单，也没告诉用户可以领 3 元券。提示词里没写清楚：薅羊毛信号只在退款、赔付类诉求中触发，查询类问题不应触发。

**原因 C：自己编时效（TC14、TC15、TC20、TC23）**
提示词只禁止“具体到账时间以外的时效”，这个说法本身有歧义；同时提示词里的示例写着“48 小时内发出新品”，等于给了模型一个可以照抄的时效。政策工具也没有返回任何时效字段，模型就自己补了一个。

**原因 D：转人工的时机过早（TC10）**
“用户坚持才转人工”的规则没有执行：模型在第一轮说明政策之后，就直接转了人工。

**原因 E：直接给多选项，没有先按政策收窄（TC03）**
29.9 元的质量问题按政策应优先给“仅退款”，模型却把三个方案一起列了出来。

另外观察到：转人工的工单有 5 条（TC16、18、20、22、23）也调用了 notify_merchant。提示词没有禁止这样做，但风险单直接推给商家并不合适，需要在提示词里明确规则。

## 4. 优先修复建议（暂未实施）

1. **把确认环节改成可配置**（提示词 + 用例）：方案唯一且金额小于 100 元时，直接建单，回复里告诉用户“已为您办理，如需更改请回复”；方案有多个时才让用户选择。同时给用例脚本补上确认或选择这一轮，让评测能覆盖完整流程。
2. **限定风险信号的适用范围**（提示词）：明确写出“物流查询、发货咨询等不涉及退款或赔付的诉求，不因售后次数转人工”；物流停滞超过 3 天时，主动告知可领 3 元券并帮用户催件。
3. **禁止自己编时效**（提示词 + 后端）：在 get_policy 里返回 `sla` 字段（如“商家 48 小时内处理”“退款 1–3 个工作日原路退回”），提示词改为“时效只能引用 get_policy.sla，没有就说以页面通知为准”，并删掉示例里的“48 小时”。
4. **在后端加硬校验**（后端）：create_after_sale_ticket 根据订单数据和政策重新校验方案，比如高金额却没转人工、超过售后期却给了退款，就返回 422；转人工的工单不允许调用 notify_merchant，或改成只发风险提醒。这样不只依赖提示词。
5. **两段式转人工**（提示词）：超出政策的诉求，第一轮先解释政策、给出可选方案，用户再次坚持才转人工。小额质量问题，按政策优先推荐唯一方案。

## 5. notify_merchant 404 问题

UI 测试里首次 notify_merchant 返回 404，本轮 30 条用例共调用 notify_merchant 7 次，**全部成功，没有复现**。从后端代码看，只有 ticket_id 不存在时才会返回 404。可能的原因有两个：
- **并行调用**：本轮多次看到 Dify 在同一步里并行调用多个工具（例如 `get_order;get_logistics`）。如果 create_after_sale_ticket 和 notify_merchant 被放在同一步并行执行，notify 就拿不到真实的工单号，只能猜一个。
- **后端重启**：UI 测试期间后端如果重启过，内存里的工单会丢失。

建议：在提示词里写明“notify_merchant 的 ticket_id 必须来自 create_after_sale_ticket 的返回值，两者不得同一步调用”；后端返回的 404 信息里带上提示（如“请先创建工单，使用返回的 ticket_id”）；要彻底避免，可以让 create_after_sale_ticket 在建单后自动通知商家。
