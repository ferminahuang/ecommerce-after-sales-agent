# 电商售后 Agent Demo：第二轮评测报告（v2）

- 时间：2026-10-10 晚（北京时间）
- 被测对象：Dify 云端 Agent，模型 deepseek-v4-flash，提示词 system_prompt_v2，6 个工具（新增 urge_logistics），后端为 v2（含硬校验、建单自动通知商家）
- 方法：与第一轮相同。streaming 接口，每条用例一个新会话，user=eval-runner，**每条用例前重启后端**
- 用例：测试用例_v2.csv。与 v1 相比，TC04 加了“选择”轮，TC09、TC10 加了“坚持”轮，用例意图不变；部分期望结果按 v2 的规则做了调整（例如方案唯一时直接建单、物流查询要催件）
- 原始记录：eval_v2/transcripts.jsonl；每条用例的后端日志：eval_v2/uvicorn_logs/；逐条判定：测试用例_评测结果_v2.xlsx
- 都只跑了一轮，样本小，模型输出也有随机性，对比结果只能作为方向参考

## 1. 冒烟测试中引用的时效
“一般 1–3 个工作日到账”“商家在 48 小时内处理售后工单”**都来自 get_policy 返回的 sla 字段**（mock_data.json → policy.sla 中的“退款到账”和“商家处理工单”），工单接口返回的 sla 里也有。不算编造。

关于定义的说明：
- 两轮的分母定义没有改。
- 工具调用正确率有一处解释需要说明：“给方案前先查政策”只适用于退款、换货、补发这类方案。高金额、情绪激动、疑似薅羊毛这些情况要求**立即转人工**，转人工不是政策里的方案，所以 v2 中 TC16、18–21、23 没查 get_policy 就转人工，不算错（v1 中这些用例都查了政策，结论不受影响）。
- TC04 在建单后调用了一次 notify_merchant 补充说明。提示词说的是“一般不要调用”，这是允许的用法，也没有报错，所以不算错误。
- 第 1 节冒烟测试中提到的时效属于 sla，不计入越权承诺。

## 3. 剩余问题和根因

**A. 直接建单的规则用过头了，跳过了诊断（TC02、TC04，TC06 也有类似情况）**
v2 的“方案唯一 / 用户已表明偏好就直接建单”被模型理解成首轮就可以建单：
- TC02（生鲜）：没有先要照片描述就建了单。
- TC04：用户说“想退”，模型就当成“已选择退货退款”，跳过了“左耳完全没声音还是声音小”的诊断。
- TC06：没有诊断就直接换货（按用例的通过标准算通过）。

根因：提示词第 4 步（诊断）和第 5 步（直接建单）没有写明先后关系，没有规定“质量问题必须先拿到现象和照片描述才能建单”。

**B. 描述与订单不符时，选择了追问而不是转人工（TC22）**
v2 把薅羊毛信号限定在“退款或赔付诉求”的范围内，模型据此把“说的是手机、订单是耳机”理解成用户可能填错了订单，于是先追问。这样做对用户更友好，但不符合用例的期望结果。根因：规则里没有区分“明显填错订单”和“刻意错配”。需要先决定产品上选哪种处理，再改提示词或用例。

**C. 索要赔付时没有先给政策内的补偿（TC27）**
用户要求赔 20 元，而且买家近 30 天售后 4 次。提示词里的两条规则同时命中：“赔付诉求 + 售后 ≥ 3 次 → 立即转人工”，以及“超出政策 → 先解释，坚持再转”。模型选了立即转人工，也就没有调用 urge_logistics，3 元券没有发出。根因：规则优先级冲突，物流停滞这一场景没有写成“先催件、发券”。

**D. 时效引用的语义有错位（TC29，轻微）**
待发货订单催件时，后端返回的 sla 是“商家处理工单 48 小时”，模型原样说成了“商家处理时效”。时效不是编的，但说的不是发货时效。根因：sla 里没有“催发货”对应的条目。

## 4. 下一步修复建议（本轮未实施）
1. **提示词：质量问题建单前必须先诊断**：拿到具体现象和照片描述之后才能建单；“直接建单”只省掉确认这一步，不省掉诊断。“想退”不算选定了退货退款，有两个方案时仍要让用户选。
2. **提示词：写明规则优先级**：物流停滞时，先调用 urge_logistics 催件并发 3 元券，再处理额外赔付诉求；额外赔付按“先解释，坚持再转”处理。“售后 ≥ 3 次”只在退款诉求下立即转人工。
3. **提示词或用例：定义“描述与订单不符”的处理方式**：追问一次确认订单号；用户仍坚持按当前订单办理，就转人工。TC22 的期望结果同步改成“追问一次，坚持则转人工”，并给它加一轮“坚持”。
4. **后端：在 sla 中增加“催发货”条目**（例如“已督促商家，具体发货时间以页面通知为准”），并在 urge_logistics 中返回这一条。
5. **后端（可选）：给 create_after_sale_ticket 加 evidence 必填校验**：质量类工单没有 evidence 时返回 422，不只依赖提示词来保证先诊断。
